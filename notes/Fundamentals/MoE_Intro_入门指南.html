01THE RESEARCH QUESTION

把课题翻译成普通话

一套模型里有很多“专家网络”。能否给需要保护的专家留更多数值精度，让其他专家用更少的位数保存，并让这套配置在实际 GPU 上划算？

ALGORITHM · 算法侧

把有限的位宽预算花在哪里？

把权重数值“刻得粗一点”通常能省空间，也会引入误差。不同专家受影响的程度可能不同，因此尝试分配不同位宽，而不是全部用同一种。

量化敏感度（quantization sensitivity）：把某部分量化后，输出或任务表现改变多少。不能只凭专家使用次数判断。

GPU DEPLOYMENT · 部署侧

省下的位数能否变成收益？

GPU 需要处理打包的数据、不同位宽的算子和不均匀的专家负载。配置越自由，执行过程可能越复杂；漂亮的压缩比也需要后端支持。

部署（deployment）：让模型在指定设备、推理框架和请求条件下稳定运行，并测出真实占用与速度。

研究可以拆成四步

① 观察专家路由频率、激活分布、权重分布、量化误差
→
② 分配位宽在候选位宽中搜索，控制质量与资源预算
→
③ 检查质量和浮点、统一位宽等基线公平比较
→
④ 实际部署验证权重文件、峰值显存、延迟与吞吐
组会可用的一句话

“我理解这个课题是在可接受的质量下降范围内，利用专家差异分配权重／激活位宽，并结合目标 GPU 的实际执行开销，寻找更好的质量、内存和速度折中。”

进一层：什么叫“联合优化”？

先约定可执行的配置集合，再决定优化谁、约束谁。例如：最小化实测延迟，同时要求模型质量下降不超过约定阈值、峰值显存不超过预算。也可以固定质量，优先降低实际模型大小。

这不是把“位宽越小”当成唯一目标。质量可能非线性变化，延迟也不一定随位宽单调下降；还要计入搜索和校准的成本。第一次组会只需问清目标和约束，无需先掌握求解算法。

02THE MINIMUM VOCABULARY

从一组数字，走到一层网络

先把 Tensor 理解成“按形状组织的数字”。数学符号可以逐步补，先看数据长什么样、经过一层后变成什么。

SCALAR / VECTOR / MATRIX

数、向量、矩阵

标量 Scalar 是一个数，如 3.0；向量 Vector 是一列或一排数；矩阵 Matrix 是按行、列排列的二维数表。

向量 [0.2, -0.5, 1.1] → shape [3]
矩阵 [[1, 2, 3], [4, 5, 6]] → [2, 3]
TENSOR

张量：多维数组

在 PyTorch 中，标量、向量、矩阵都可用 Tensor 表示。多一个维度通常只是多一个索引，例如“第几条文本、第几个 token、第几个特征”。

[batch, tokens, hidden] = [2, 5, 8]
2 条文本 × 每条 5 个位置 × 8 个特征
SHAPE / DTYPE / DEVICE

看 Tensor 先看三个属性

shape 是形状，各维大小决定能否相乘；dtype 是数字格式，影响精度与占用；device 表示数据在 CPU 还是 GPU。

x.shape · x.dtype · x.device
元素数 × 每元素字节数 ≈ 原始数据大小
LINEAR LAYER / FULLY CONNECTED

线性层：把特征重新组合

用一组固定权重，把输入的多个特征组合成新的特征。nn.Linear(3, 4) 接收每个位置的 3 个数，输出 4 个数；默认也有偏置 bias。

X: [2, 3] · W: [4, 3]
Y = X @ W.T + b → [2, 4]

@ 表示矩阵乘法；W.T 表示把权重矩阵的行列交换。PyTorch 将 Linear 的权重保存为 [输出维度, 输入维度]。有偏置时严格说是仿射变换，入门时先掌握上面的计算关系即可。

Weight 和 Activation：两个主角

两者都可以是 Tensor，区别在于它们从哪里来
概念直观理解和本课题的关系
权重 Weight，W训练得到并保存的参数；普通推理时通常不更新。权重量化会改变模型保存方式与运行时读取的数据量。
激活 Activation，A给定输入在各层计算出的中间数值，例如 Linear 的输入／输出。随文本、位置和批次变化；激活量化常需代表性数据确定范围。
两个词义提醒

Activation 不等于 activation function（激活函数）；后者是 SiLU、ReLU 等非线性运算。Dense layer 常指全连接层；这里的 Dense model 指 token 使用同一套 FFN 的常规模型，与按 token 选少量专家的 Sparse MoE 相对。

基础参考：PyTorch Tensors 教程 · torch.nn.Linear 文档

03HOW GENERATION WORKS

LLM 怎样一个个生成 token？

先看常见的自回归、仅解码器 Transformer：输入文本，预测下一个 token，再把新 token 接回去，继续预测。

文本 → TokenTokenizer 分词并转成编号
→
编号 → 特征Embedding 查表得到向量
→
多层 TransformerAttention 与 FFN 逐层处理
→
预测 → 新 Token得到分数，选取下一个编号

Token 是分词单位，可能是字、词的一部分或符号，不总是一个汉字／单词。Inference（推理）使用已有模型做预测；Training（训练）还需要计算梯度并更新参数。

ATTENTION · 注意力

从上下文取信息

当前位置根据 Query（查询）与历史 Key（键）的匹配程度，对 Value（值）加权汇总。入门先记：它让不同 token 之间交流；生成时不能偷看未来 token。

FFN · 前馈网络

加工每个位置的特征

Feed-Forward Network 通常由线性变换和非线性函数组成。它对各 token 的特征向量做处理。一个 Transformer 层还包含残差连接、归一化等结构。

一次请求的两个阶段

阶段在做什么为什么要分开测
预填充 Prefill并行处理 prompt 中的 token，建立 KV cache，并得到预测首个生成 token 所需的信息。prompt 长度影响明显；与首 token 等待时间有关。
解码 Decode常规自回归生成中，每个请求逐步生成新 token，复用缓存的历史 Key/Value。影响后续输出速度；batch、上下文长度会改变瓶颈。

KV cache（键值缓存） 让模型不用每一步重新计算过去 token 的 K/V，但缓存也占显存。普通全注意力的缓存通常随上下文、并发请求增加；滑动窗口等架构有所不同。降低权重位宽，不会自动缩小 KV cache。

MoE 改了哪里？

Mixture of Experts（混合专家） 通常把部分 FFN 换成多个专家网络，由 Router / Gating（路由器／门控） 为每个 token 选择少量专家。Top-k 表示选出路由分数靠前的 k 个，再按路由权重组合它们的输出。

激活参数少，不代表全部参数少

Top-2 只意味着这个 token 在该层调用少量专家。常规 GPU 常驻方案仍要保存其他专家权重；把专家卸载到 CPU／磁盘（offloading）则可能带来额外搬运延迟。这正是 MoE 压缩值得研究的原因之一。

延伸阅读：Hugging Face · Mixture of Experts Explained · KV cache 文档

04LESS BITS, MORE DECISIONS

位宽与量化：少用几位，付出什么？

Bit-width（位宽）是表示一个数使用的二进制位数。位数少，能表示的数值更有限；量化 Quantization 就是把原来的数映射到较少的可表示值上。

常见格式速查 · 先记性质，无需背二进制布局
格式每元素理论占用初学者要知道的特点
FP1616 bit = 2 字节16 位浮点数，有小数与指数；常见推理基线之一。
BF1616 bit = 2 字节与 FP16 大小相同；指数范围更大，有效数值精度较低。两者并非同一格式。
INT88 bit = 1 字节8 位整数编码，最多 256 个码；需结合 scale 等参数还原数值。
INT44 bit = 0.5 字节最多 16 个码；通常要把两个 4 位编码打包进一个字节，才获得相应占用。

量化像把连续的刻度，改成有限的格点

简单对称量化可写成下面两步。Scale（缩放因子 s） 决定相邻格点有多远；先除以 s、舍入到最近整数并限制整数范围，再乘回 s，得到近似值。

整数码 q = clamp(round(w / s), q_min, q_max) 近似权重 w_hat = q × s

clamp 表示把超出范围的值截到端点。非对称量化还常使用 zero-point（零点偏移）。实际方法可按整个 Tensor、输出通道或小组 group 使用不同 scale；分组更细通常增加元数据和实现复杂度。

PTQ · POST-TRAINING QUANTIZATION

训练后量化

在已有模型上做量化。常用一小批代表性 Calibration data（校准数据） 观察数值范围、估计误差或搜索位宽。多数入门 PTQ 路线无需重新做完整训练，但仍有校准计算成本。

QAT（Quantization-Aware Training，量化感知训练）则把量化影响带进训练／微调流程，第一周可以先不做。

W4A8 · W = WEIGHT, A = ACTIVATION

读懂位宽缩写

W4A8：约定算子中的权重 4 bit、激活 8 bit。W4A16 常用于表示 4 位权重、16 位浮点激活；还要明确激活用 FP16 还是 BF16。

缩写不说明累加器精度，也不保证 Router、Attention、KV cache 或全模型都用同一种格式。W-only 只量化权重；W+A 同时考虑权重与激活。

混合位宽：试着给 4 个专家分配预算

假设四个专家各有 2.5 亿参数，总计 10 亿；只算专家权重的原始数据，不含共享层、scale、打包填充或运行时开销。改变位宽，观察理论体积。

教学算例 · 不预测模型质量或实际速度
6.0 bit专家平均位宽
0.75 GB理论纯权重体积
2.67×相对全 16 位的体积压缩比

默认配置 [4, 4, 8, 8] 的平均值为 6 bit。这里 1 GB = 10⁹ 字节；0.75 GB 约为 0.70 GiB。修改配置只是在算空间账，不能据此判断谁“应该”用 4 bit。

参数量加权平均位宽 = Σ(Nᵢ × bᵢ) / ΣNᵢ 纯权重字节数 ≈ Σ(Nᵢ × bᵢ) / 8

Nᵢ 是某部分参数量，bᵢ 是它的位宽。专家大小不同时，不能直接平均各专家的 bit 数。报告时说明分母是“专家部分”还是“全模型”；路由频率加权平均也不能替代静态存储的参数量加权平均。

为什么不能把低频专家一律压到最低位宽？

路由频率只是一个信号。低频专家可能服务少量但重要的任务；高频专家也未必最敏感。需要结合激活范围与异常值、参数分布、重建误差和下游任务变化。校准文本不具代表性时，观察到的频率也可能偏差很大。

专家内不同 Linear 也可能有不同敏感度。位宽分配究竟按“专家整体”还是“专家内线性块”，以及是否允许随输入动态变化，都是需要确认的研究边界。

量化概念参考：Hugging Face · Quantization concepts

05THE GAP BETWEEN A FORMULA AND A GPU

压得更小，为什么可能没有更快？

“数值看起来像低比特”“文件确实变小”“GPU 执行更快”是三件要分别证明的事。

做到了哪一步能说明什么还不能说明什么
量化仿真
Fake / Simulated Quantization		round / clamp 后反量化回浮点，观察误差对输出的影响。若仍保存浮点并做浮点矩阵乘法，不能证明文件变小或低位算子加速。
真实压缩存储
Packed Weights		权重以低位格式打包，并保存 scale、必要的零点和布局信息。文件小不等于峰值显存同比下降，更不等于端到端延迟缩短。
实际低位后端
Low-bit Kernels / Backend		对应算子读取低位数据，在目标 GPU 上执行；可能在内核中反量化后用浮点运算。单个矩阵乘法快，不保证整个生成请求同比加速。

Kernel（计算内核） 是 GPU 上执行具体运算的一段程序。GEMM 是通用矩阵乘法；Grouped GEMM 把多组矩阵乘法组织起来执行，适合专家各有一批 token 的情形。不同专家位宽混杂时，组织和调度会更难。

收益可能从哪里来？

  • 从显存读取的权重字节数减少。
  • 支持相应格式时，矩阵运算可能更高效。
  • 模型能装进更少的 GPU，或减少 CPU–GPU 搬运。

小 batch 解码常容易受权重读取影响；大 batch 或长 prompt 又可能呈现不同瓶颈。都需要测量。

收益可能被什么抵消？

  • 解包、反量化、格式转换的额外工作。
  • 专家 token 太少，矩阵过小，GPU 吃不满。
  • 位宽分组产生更多 kernel 启动与调度。
  • 专家负载不均，跨卡通信或 KV cache 成为瓶颈。
组会必须问到“具体能跑哪一种”

GPU 宣称支持 INT4，不代表现有推理框架能高效执行“同一 MoE 层中部分专家 W4、部分 W8”。需要确认GPU 型号 + 后端 + 精确格式 + group size + tensor shape + 混合位宽调度这一整套组合。

实例：MxMoE 论文 将位宽选择与性能模型、混合精度 GroupGEMM 结合；这说明部署成本本身也是研究问题。

06WHAT COUNTS AS A GOOD RESULT?

先约定量尺，再说“更好”

“模型精度基本保持”需要变成一个阈值；“节省内存”需要说明统计口径；“更快”需要说明请求条件。

实验结果至少分开报告这四组指标
维度看什么怎么避免误读
模型质量
Quality		语言建模困惑度 PPL（通常越低越好）；任务准确率／得分（通常越高越好）。固定模型、tokenizer、数据集、提示模板和评测设置。少量聊天样例只能做直观检查。
权重、存储与显存
Weights / Storage / VRAM		参数量加权平均位宽、纯权重数据量、实际文件大小、加载后与运行峰值显存。文件还含元数据；显存还含 KV cache、中间激活、工作区、缓存和通信缓冲。分别报告。
访存与带宽
Memory Traffic / Bandwidth		实际搬运字节数、有效传输速率与相关等待；可结合 profiler 观察瓶颈。文件缩小只是可能少读数据；不能直接声称 GPU 带宽“提高”。区分显存与跨卡／CPU–GPU 链路。
速度与吞吐
Latency / Throughput		首 token 延迟 TTFT、后续每 token 时间、请求总时间、输出 token/s。固定输入／输出长度、batch、并发和设备；单请求低延迟与多请求高吞吐是不同目标。
再解释一点：PPL、TTFT、TPOT 和 token/s

Perplexity（困惑度） 衡量模型在给定文本上预测下一个 token 的情况。比较 PPL 时要使用相同数据和计算设置；跨 tokenizer 的值不能随便横向比较。

TTFT（Time to First Token）：从约定的请求起点到收到首个 token 的时间。服务场景可能包含排队、分词和 prefill，报告时写清边界。TPOT（Time per Output Token）：后续输出 token 的平均耗时；ITL 指相邻 token 的到达间隔。

输出吞吐 = 测量窗口内生成的输出 token 总数 ÷ 时间。多个请求并发的总 token/s 不等于单个用户的生成速度。若报告 p50／p95，它们分别是中位数／95% 分位延迟。

一份公平对照实验，先固定这些条件

  1. 基线 Baseline：同一模型的 FP16／BF16、统一位宽量化、你的混合位宽方案；最好加一个简单位宽分配方法，验证复杂搜索是否值得。
  2. 质量预算：例如“任务分数最多下降多少个百分点”“PPL 最多增加多少”。这是待组内确定的标准，不能自行宣称“无损”。
  3. 数据分工：校准集用于确定量化参数和统计；验证集用于选方案；测试集留给最终报告，避免用测试结果反复调参。
  4. 性能条件：记录 GPU 型号／数量、软件版本、后端、输入输出 token 长度、batch／并发、缓存策略和精确量化配置。
  5. 测量方法：先预热，多次重复并报告波动；GPU 运算异步，低层计时要用 CUDA events 或正确同步。用经过验证的 benchmark 更省心。
第一张结果表可以很朴素

模型与版本｜方法／位宽配置｜PPL／任务分数｜权重文件 GB｜峰值显存 GiB｜TTFT ms｜Decode ms/token｜输出 token/s｜请求与软件配置。暂未测出的值写“未测”，不要用理论压缩比代替实测值。

显存口径也要一致：PyTorch 的 allocated（张量分配）与 reserved（缓存分配器预留）不同；进程总占用还可能包含其他部分。多卡实验同时写明每卡和总量。

09A SMALL, HONEST FIRST EXPERIMENT

用 PyTorch，亲手看一次误差

这是单个 Linear 权重的对称、按输出通道量化练习。只需安装了 PyTorch 的 Python 环境；使用 CPU，不下载模型。它帮助理解量化，不实现 MoE 部署。

先读这条限制

示例将量化码放在 int8 容器里，再恢复为 float32 做矩阵乘法。4 位时没有打包；同时保留原权重和重建权重。因此它不是实际 INT4 推理，也没有展示真实内存节省或加速。

把下方代码保存为 quant_demo.py，在已安装 PyTorch 的环境运行 python quant_demo.py。建议沿用组内环境；安装方式以 PyTorch 官方安装页为准。

quant_demo.py · 教学仿真 · CPU
import torch
import torch.nn.functional as F

torch.manual_seed(0)

# 3 个输入样本，每个 8 个特征；输出为 4 个特征
x = torch.randn(3, 8, dtype=torch.float32)
weight = torch.randn(4, 8, dtype=torch.float32)
bias = torch.randn(4, dtype=torch.float32)


def quantize_dequantize(w, bits):
    if bits not in (4, 8):
        raise ValueError("本例只演示 4 bit 与 8 bit")

    # 使用对称范围：4 bit 为 [-7, 7]；8 bit 为 [-127, 127]
    # 为了对称，各留一个整数码不用；不是所有量化方法都这样做
    qmax = 2 ** (bits - 1) - 1

    # 每个输出通道（每行）一个 scale，shape = [4, 1]
    row_max = w.abs().amax(dim=1, keepdim=True)
    # 全零行使用 scale=1，避免除零；其他行按最大绝对值缩放
    scale = torch.where(row_max > 0, row_max / qmax,
                        torch.ones_like(row_max))

    q = torch.round(w / scale).clamp(-qmax, qmax).to(torch.int8)
    w_hat = q.to(torch.float32) * scale
    return q, scale, w_hat


with torch.inference_mode():
    y_ref = F.linear(x, weight, bias)  # x @ weight.T + bias
    print("shape:", x.shape, weight.shape, y_ref.shape)

    for bits in (8, 4):
        q, scale, w_hat = quantize_dequantize(weight, bits)
        y_hat = F.linear(x, w_hat, bias)  # 仍然是 float32 运算

        weight_mse = (weight - w_hat).square().mean().item()
        output_mse = (y_ref - y_hat).square().mean().item()
        code_bytes = q.numel() * q.element_size()
        scale_bytes = scale.numel() * scale.element_size()
        ideal_bytes = weight.numel() * bits / 8

        print(f"\n{bits} bit: W-MSE={weight_mse:.6f}, "
              f"Y-MSE={output_mse:.6f}")
        print(f"整数码容器={code_bytes} B, scale={scale_bytes} B")
        print(f"理想打包的纯权重={ideal_bytes:.0f} B；本例未打包")

运行后，试着回答这三个问题

  1. 形状为什么是 [3, 8] → [3, 4]？把它对应回 F.linear 的公式。
  2. 4 位与 8 位的 MSE 有什么差别？MSE 是均方误差，越小表示这里的重建越接近。它不能直接代替语言模型任务质量。
  3. 为什么整数码容器两次都是 32 B？32 个码都存成 int8；4 位的理想纯权重为 16 B，8 位为 32 B。另有 4 个 float32 scale，共 16 B；这里还没计其他张量。

这个练习只量化 W，输入 x 与 bias 都保留 float32；不是 W4A8。随机输入的输出误差也不能代表真实 MoE。下一步可以尝试一组真实层权重或代表性输入，但应先和组内确认模型与数据。

论文 15 分钟初筛法

  1. 摘要 + 主图：它解决的是质量、空间还是速度？量化粒度是什么？
  2. 实验表 + 设置：用了什么模型、GPU、数据和基线？速度是 kernel、整层还是端到端？
  3. 方法概览：重要性怎样估计？位宽怎么选？是否需要校准、训练或内核生成？
  4. 记一张对照卡：“输入条件 → 方法 → 实测收益 → 成本与限制 → 我能复现哪一部分”。暂不懂的公式先做标记。
